# Campus Events · 校园活动报名与签到系统设计方案

设计日期：2026-10-29。状态：完整个人项目版本已实现并上传 GitHub；MySQL 8.4 与 Linux race 已在远程 CI 中验证。完整 Docker Compose 和性能压测尚待执行，验收见《完整版验收.md》。

实现差异：页面已改为 Go 内嵌静态资源；增加 auth_sessions 表实现当前会话撤销；Redis 缓存命中仍查询实时名额，不宣称减少 SQL 请求数。用户决定先完成全部功能再拆解学习，原阶段安排保留作为设计历史。

## 1. 定位与范围

面向只学过 Go 基础语法、准备找后端实习或应届岗位的开发者。目标是完成一个业务闭环，并能解释核心代码、验证结果和设计局限。

场景：社团或老师发布有限名额的讲座、工作坊，学生浏览活动、报名、取消报名，组织者在现场核验签到。

第一版集中在账号、活动、报名三个模块，使用一个 Go 服务和一个 MySQL 数据库。基础流程完成后增加 Redis 缓存与简单演示页面。每阶段交付能运行的版本和对应的阅读、练习文档。

明确暂缓：支付、秒杀式 Redis 预扣库存、候补队列、消息队列、推荐算法、聊天、微服务、Kubernetes、二维码防伪和外部邮件短信。后续扩展必须有具体需求，不能仅为增加技术名词。

## 2. 使用者与演示流程

| 使用者 | 能做什么 |
| --- | --- |
| 游客 | 查看已发布活动列表和详情、注册和登录 |
| 学生 | 查看活动、报名、取消自己的报名、查看自己的报名记录 |
| 组织者 | 创建和发布自己的活动、查看本活动名单、核验签到 |

公开注册只创建学生账号。组织者通过本地初始化命令创建，客户端不能选择角色。组织者只能管理自己创建的活动。

演示顺序：组织者创建一场 3 个名额的活动并发布；学生报名；重复点击报名；另一个学生取消并释放名额；展示已满提示；组织者查看名单；在签到时间窗口内核验签到。另用脚本演示并发报名和重复取消。

演示数据提供一场正在报名的活动和一场正在进行的活动，不通过篡改服务器时间演示。

## 4. 数据模型

| 表 | 主要字段 | 约束与查询索引 |
| --- | --- | --- |
| users | id、username、password_hash、role、created_at | username 唯一；role 为 student 或 organizer |
| events | id、organizer_id、title、description、location、capacity、registered_count、status、registration_starts_at、registration_ends_at、starts_at、ends_at、created_at | organizer_id 外键；(status,id) 和 (organizer_id,id) 索引 |
| registrations | id、event_id、user_id、status、checked_in_at、created_at、updated_at | (event_id,user_id) 唯一；(user_id,id)、(event_id,status,id) 索引；event_id、user_id 外键 |

events.status 只保存 draft / published。报名未开始、报名中、报名截止、进行中、已结束由时间推导，不另设定时任务更新状态。

registrations.status 为 active / cancelled，签到使用 checked_in_at 表示，不额外增加一组相互重叠的状态。registered_count 统计 active 记录，签到不改变报名状态和人数。

基本约束：capacity > 0，0 <= registered_count <= capacity；报名开始 < 报名截止 <= 活动开始 < 活动结束。数据库采用 InnoDB、utf8mb4；时间写入和比较统一使用 UTC，界面按 Asia/Shanghai 显示。

同一学生同一活动始终只有一条报名记录，取消后重新报名更新原记录。第一版不提供报名历史流水、用户删除、活动删除、整场活动撤销。发布后不再修改时间与名额，避免扩大状态处理范围。

列表按 id DESC 使用 ID 游标分页，默认 20 条，最多 100 条。此顺序表示创建顺序，不提供复杂排序与全文搜索。

## 5. 业务规则和正确性

### 5.1 报名

1. 从认证上下文获取学生身份，拒绝客户端代填 user_id。
2. 开启数据库事务，按主键 SELECT 活动 FOR UPDATE。
3. 校验活动已发布，且当前时间在报名区间内。
4. 读取 (event_id,user_id) 报名记录；若已 active，返回原记录，不再次占名额。
5. 若记录不存在或已取消，检查 registered_count < capacity。
6. 创建 active 报名记录，或将 cancelled 改为 active；同时将 registered_count 加 1。
7. 全部成功才提交，否则回滚。

对外只在事务提交成功后返回成功。已 active 的重复报名在报名窗口内返回相同业务结果；窗口外的新请求返回报名已关闭，可通过“我的报名”确认此前结果。

同一活动的名额修改通过同一行锁串行执行。唯一约束作为额外的数据完整性保护。事务内部所有 SQL 必须使用 tx，不能混用外部 db。不能用进程内互斥锁代替数据库保护，否则运行两个服务进程后无法协调。

这是便于理解和验证的初版方案，热门活动的同一行会成为竞争点。只报告实际测试的吞吐、延迟和错误，不预先承诺承载规模。

### 5.2 取消

开启事务，先锁活动行，再读取报名记录，与报名保持相同锁顺序。仅允许本人在报名截止前取消。active 转为 cancelled 时人数减 1；已 cancelled 的重复取消返回原结果，不再次减人数。未报名返回不存在。报名截止后关闭取消入口，已签到也不能取消。

### 5.3 签到

仅活动组织者可以核验，在活动开始到结束的时间区间内操作。必须存在 active 报名记录。以条件更新将空的 checked_in_at 设置为当前时间；已经签到时返回原签到结果。第一版为组织者在名单页人工核验，不声称具备二维码防伪能力。

### 5.4 错误处理与认证

使用明确 HTTP 状态码和稳定业务错误码，例如 400 参数错误、401 未登录、403 无权限、404 不存在、409 名额已满或报名时间冲突、503 暂时不可用。日志记录 request_id 和具体内部错误，响应不回传 SQL、密码或令牌。

密码只存 bcrypt 哈希。JWT 校验签名、到期时间和用户身份；权限取自服务端用户信息，不接受请求体传入角色。访问令牌有效期 2 小时，不做刷新令牌和密码找回；实际实现增加 auth_sessions 表，退出会删除当前服务端会话，使该令牌立即失效。

处理数据库锁等待和死锁错误时回滚并返回可重试错误。只有在测试证实需要时再增加有界重试，重试整段事务而非失败的单条 SQL。

## 7. Redis 的边界

Redis 在前三阶段完成后加入。只缓存已发布活动的标题、描述、地点和时间等公开信息，不缓存密码、JWT、报名名单，也不使用缓存决定是否允许报名。

名额和本人报名状态从 MySQL 查询，避免把过期缓存当作剩余名额事实。缓存失败降级查数据库。公开静态信息采用固定短 TTL；如后续允许编辑已发布信息，提交数据库事务后删除缓存，并明确允许短暂的展示延迟。

有了可复现的热点未命中场景，再考虑 singleflight。它只合并同一个 Go 进程内的并发加载，不能声称实现跨实例请求合并。缓存效果必须在相同数据、请求和机器条件下比较 SQL 查询数量与延迟。

## 9. 必须验证的场景

以下为验收计划，当前没有任何已测结果。涉及 MySQL 事务和锁的测试使用独立测试数据库，不能用 SQLite 或仅靠 mock 代替；测试数据通过独立配置与开发数据隔离，不删除用户已有数据库。

| 场景 | 预期结果 |
| --- | --- |
| 20 个不同学生竞争 5 个名额 | 恰好 5 条 active 报名，registered_count = 5，其余收到名额不足；前提是无基础设施错误 |
| 同一学生并发报名 20 次 | 只有一条报名记录，只占一个名额，响应指向同一记录 |
| 同一学生重复取消 | 只释放一个名额，人数不会变负数 |
| 取消后重新报名 | 复用原记录，重新占用一个名额 |
| 报名与取消交错执行 | 结束后人数等于 active 记录数，且不超过容量 |
| 报名记录写入失败 | 人数与报名记录一起回滚，不出现部分成功 |
| 组织者访问其他人的名单 | 拒绝访问，不泄露报名信息 |
| 报名区间之外操作 | 返回明确业务错误，不改变名额 |
| 重复签到 | 签到时间不重复覆盖，人数不变化 |
| Redis 不可用 | 公开详情回源查询，报名和取消仍可正常使用 |

并发脚本使用有上限的 worker 和请求超时，准备足够的不同用户，区分业务拒绝、超时和服务器错误。完成后直接查询数据库验证不变量；测试竞争正确性与测量吞吐分开执行。缓存性能测试使用固定数据集，分别记录启用前后的请求数、并发数、P50/P95、错误率和数据库查询数量。
