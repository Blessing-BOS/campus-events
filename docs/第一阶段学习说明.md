# 第一阶段：理解你自己的第一个 Go 后端接口

历史阶段文档：完整版本已继续实现，当前能力以 README 和 API.md 为准。按用户要求，完整项目完成后再系统拆解学习。

这一阶段只需要理解“收到 HTTP 请求，查询活动，返回 JSON”。登录、并发报名和缓存会在后面加入。

## 先运行，再读代码

按 README 的只读演示模式启动服务，依次访问：

1. `/healthz`：观察 data_source 为 demo。
2. `/api/v1/events`：看到两个公开活动。
3. `/api/v1/events/1`：看到单个活动。
4. `/api/v1/events/3`：看到 404，因为这条演示数据是草稿。
5. `/api/v1/events?limit=1`：观察 has_more 和 next_before_id。
6. `/api/v1/events?limit=0`：观察参数错误。

打开浏览器能看到 JSON，就说明你的服务已经在处理请求。此时还没有前端页面。

## 按一次请求读代码

```text
GET /api/v1/events?limit=1
  → internal/httpapi/router.go：匹配路径
  → internal/event/handler.go：读取并检查 limit
  → internal/event/service.go：向数据源多要一条，用来判断还有没有下一页
  → internal/event/demo.go 或 repository.go：取出已发布活动
  → internal/event/entity.go：计算状态，转为公开 JSON 结构
  → Handler 返回 HTTP 200 和 JSON
```

建议阅读顺序：

| 次序 | 文件 | 只需先看懂什么 |
| --- | --- | --- |
| 1 | cmd/server/main.go | 创建依赖、选择数据源、启动服务 |
| 2 | internal/httpapi/router.go | 一个 URL 对应哪个处理函数 |
| 3 | internal/event/handler.go | URL 参数如何变成数字、何时返回 400 |
| 4 | internal/event/service.go | 如何决定是否还有下一页 |
| 5 | internal/event/demo.go | 切片、循环、排序和筛选 |
| 6 | internal/event/repository.go | 参数化查询、WHERE、ORDER、LIMIT |
| 7 | internal/event/entity.go | Go 结构体、JSON 标签、时间比较 |

先沿一条成功请求阅读，再看失败分支。配置、服务关闭、数据库连接池等代码可以在主流程读懂后再看，不要求第一次全部掌握。

## 必须理解的几个区别

- **Handler 和 Service**：前者处理 HTTP，后者处理业务规则。将来业务不应只存在于某个页面里。
- **结构体和 JSON**：结构体是 Go 内存里的数据；JSON 是响应传输时的表示。`json:"title"` 指定输出字段名。
- **演示模式和数据库模式**：演示模式从内存切片读取；MySQL 模式真的执行 SQL。两者提供相同查询能力，但不能把演示模式当成数据库性能或事务验证。
- **interface 的作用**：当前只有两个存储操作，因为确实存在演示和 MySQL 两种实现，也需要验证查询失败时的 HTTP 行为。先理解“同样的调用可以接不同数据来源”即可。
- **context.Context**：随请求传给查询。当请求取消或超时，查询应有机会停止，避免一直占用资源。
- **defer**：安排函数结束时释放资源，例如关闭连接、取消超时上下文。

## 三个理解问题

1. 为什么 `limit=1` 时，Service 会向数据源请求两条？如果只取一条，怎样知道有没有下一页？
2. 为什么查询公开活动必须在数据源层筛选 published，而不能只在页面上隐藏草稿？
3. 为什么 `/healthz` 成功，`/readyz` 仍有可能失败？

参考回答：多取一条判断下一页；页面隐藏不能阻止别人直接调用接口；进程存活不代表数据库及活动表可用。面试时应能指向代码解释，而不只复述这三句话。

## 一个小练习

将默认每页数量从 20 改为 5，保留最大值 100。找到生效位置，启动服务，分别访问“不传 limit”“limit=1”“limit=101”，确认默认值变化没有破坏显式参数与校验。

练习完成后说明：改了哪个文件、为什么不用改数据库、怎样确认行为正确。这比单纯记住接口名称更接近面试中的实际追问。
